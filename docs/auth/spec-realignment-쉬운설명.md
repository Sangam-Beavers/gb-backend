# 인증 방식이 왜 바뀌었고, 명세서를 왜 고쳐야 하나 (쉬운 설명)

> 이 문서는 `spec-realignment-auth-b.md`(팀 논의용 정리표)가 어렵게 느껴지는 분들을 위해,
> **처음 보는 사람도 이해할 수 있게** 풀어쓴 거예요. 이걸 먼저 읽고 정리표를 보면 훨씬 잘 읽혀요.

---

## 0. 한 문장으로

> **로그인·비밀번호 관리를 "우리가 직접" 하다가 → "전문 업체(Authentik)에게 맡기는" 방식으로 바꿨어요.**
> 그런데 명세서는 아직 "우리가 직접" 하던 시절 기준으로 적혀 있어서, 지금이랑 안 맞아요. 그래서 고쳐야 해요.

---

## 1. 비유로 시작해요 — 놀이공원 입장 팔찌

우리 앱을 **놀이공원**이라고 해볼게요. 손님이 들어오려면 **입장 팔찌**가 필요해요. (이 팔찌가 바로 로그인 토큰이에요.)

이 팔찌를 **누가 만드냐**가 이번 변화의 핵심이에요.

### 옛날 방식 (= "방식 A") — 우리가 직접 다 함

```
손님 → 우리 매표소에 아이디/비번 제출
       우리가 비번 맞는지 확인
       우리가 팔찌(토큰)를 직접 제작해서 발급
       우리가 손님 비번도 보관
```

우리가 **매표소 + 팔찌 공장 + 비번 금고**를 전부 운영하는 거예요. 일이 많고, 비번을 우리가 들고 있어서 위험 부담도 커요.

### 새 방식 (= "방식 B") — 전문 발급소(Authentik)에 맡김

```
손님 → 옆 건물 "공식 발급소(Authentik)"에서 로그인
       발급소가 비번 확인하고 팔찌(토큰)를 만들어 줌
       손님이 그 팔찌를 차고 우리 놀이공원에 옴
       우리는 팔찌가 진짜인지 "검사만" 함
```

이제 우리는 **검표원**만 해요. 팔찌 만드는 일, 비번 보관은 전문 발급소(Authentik)가 다 해줘요.

> **그래서 "방식 B = 우리는 검사(검증)만 한다"** 예요. 이 한 문장이 전부예요.

---

## 2. 그럼 뭐가 좋아졌어요?

- **비번을 우리가 안 들고 있어요** → 우리 DB가 털려도 손님 비번은 안전해요. (발급소에만 있음)
- **팔찌 만드는 복잡한 일을 전문가가 함** → 보안 까다로운 부분을 우리가 직접 안 만들어도 돼요.
- **개발용·운영용을 똑같이** → 개발 땐 Authentik, 운영 땐 Cognito라는 발급소를 쓰는데, 둘 다 같은 표준이라 코드를 거의 안 바꿔도 돼요.

여기서 용어 하나만:
- **IdP** = "발급소"를 가리키는 정식 용어 (Identity Provider). 우리 경우엔 **Authentik = IdP**예요.

---

## 3. 그래서 "왜 명세서를 고쳐야" 하나요?

명세서는 우리가 **옛날 방식(방식 A)으로 만들기로 했을 때** 적은 문서예요. 그래서 곳곳에 이런 말이 적혀 있어요:

- "백엔드가 토큰을 발급한다" ← 이제 발급은 Authentik이 해요. **틀림.**
- "비밀번호를 해시해서 저장한다" ← 이제 비번은 우리가 안 가져요. **틀림.**
- "로그인 API(`/auth/login`)" ← 이제 로그인은 손님이 발급소에서 직접 해요. 우리 API 없어요. **틀림.**

즉 **문서랑 실제 코드가 안 맞는 상태**예요. 이대로 두면 — 나중에 이 문서 보고 작업하는 사람이 "어? 토큰 발급 코드가 어디 있지?" 하고 헤매게 돼요. 그래서 문서를 지금 방식(방식 B)에 맞게 고쳐야 해요.

> **비유:** 가게 메뉴판엔 "짜장면 팝니다"라고 적혀 있는데, 실제 주방은 이제 짜장면을 안 만들고 옆 가게에서 받아와요. 메뉴판을 고쳐야 손님도 직원도 안 헷갈리죠. 그 "메뉴판 고치기"가 명세서 갱신이에요.

---

## 4. 그래서 각 기능이 어떻게 바뀌나요? (제일 중요)

명세서에 적힌 로그인 관련 기능들이, 방식 B에서 어떻게 되는지 쉬운 말로 정리했어요.

### ✅ 그대로 두면 되는 것
- **회원가입** — 우리가 계속 받아요. (가입할 때 닉네임·국적·언어 같은 우리만 필요한 정보가 있어서.) 단, 비번은 우리가 저장 안 하고 발급소에 등록만 해요.
- **이메일/닉네임 중복확인** — 방식이랑 상관없이 그대로 동작. (이미 구현 완료)

### ❌ 없애야 하는 것 (이제 우리 일이 아님)
- **이메일 로그인 API (`/auth/login`)** — 로그인은 손님이 발급소에서 직접. 우리 API 없음.
- **토큰 재발급 (`/auth/reissue`)** — 팔찌 갱신도 발급소 일.
- 둘 다 "옛날 방식 잔재"라 명세서에서 빼거나 "폐기됨"이라고 표시해야 해요.

### ⚠️ 다시 정해야 하는 것 (팀이 의논 필요)
- **구글 로그인** — 명세엔 "우리가 구글이랑 직접 처리"라고 돼 있는데, 방식 B에선 **발급소(Authentik)가 구글이랑 연결**해줘요. 그럼 우리가 만들 게 거의 없어요. → 이 방향이 맞는지 팀이 확정.
- **로그아웃** — 방식 B에선 우리가 팔찌를 안 들고 있어서, "로그아웃을 어떻게 처리할지" 방법이 여러 개예요. (그냥 손님 폰에서 팔찌 버리기 / 발급소 세션까지 끊기 등) → 하나 골라야 함.
- **비밀번호 찾기/재설정** — 비번이 발급소에 있으니 재설정도 발급소 경유. + 재설정 메일 보내려면 **메일 발송 기능(SMTP)** 이 있어야 함. → 메일 되는지 확인 필요.
- **가입 인증 이메일** — 이것도 **메일 발송(SMTP)** 이 있어야 가능. → 확인 필요.

---

## 5. 결국 팀이 정해야 할 것 (회의 안건)

복잡해 보이지만, 사실 **결정할 건 이 4가지**예요:

1. **`/auth/login`, `/auth/reissue` 없애는 거 OK?** (이미 코드엔 없음 — 문서만 정리)
2. **구글 로그인을 "발급소가 처리"하는 방식으로 갈까?** (그러면 우리 백엔드 일 거의 없음)
3. **로그아웃은 어떻게?** (제일 단순한 "폰에서 팔찌 버리기"로 충분한지)
4. **메일 발송(SMTP)이 개발 환경에 준비돼 있나? 없으면 누가 준비?** (비번재설정·이메일인증이 여기 달림)

이 4개만 정해지면, 남은 인증 작업들을 바로 시작할 수 있어요.

---

## 6. 핵심만 다시 (TL;DR)

- 우리는 이제 로그인/비번/팔찌(토큰)를 **직접 안 만들고, 발급소(Authentik)에 맡겨요.** 우리는 **검사만** 해요. (= 방식 B)
- 명세서는 아직 **옛날(직접 만들던) 기준**이라, 지금이랑 안 맞아서 **고쳐야 해요.**
- 회원가입·중복확인은 그대로, 로그인·토큰재발급은 폐기, 구글/로그아웃/비번재설정/이메일인증은 **방법을 다시 정해야** 해요.
- 그 "다시 정할 것"이 위 5장의 **회의 안건 4개**예요.
